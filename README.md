# OZON Price Monitor Bot

Telegram-бот, который отслеживает цены товаров на OZON и уведомляет пользователя
при резком снижении цены (по абсолютному порогу и/или проценту падения).

## Стек

Python, aiogram 3 (Telegram-бот), FastAPI (health/metrics), SQLAlchemy + PostgreSQL
(хранение товаров и истории цен), Redis (FSM-хранилище состояний бота), asyncio
(планировщик проверок), Docker/Docker Compose.

## Парсинг OZON

У OZON нет публичного API для получения цены произвольного товара по каталогу
(Seller API отдаёт только товары самого продавца), поэтому используется скрапинг
витрины сайта, `app/services/ozon_parser.py`:

1. **`api`** — запрос к внутреннему JSON-эндпоинту OZON (`api.ozon.ru/composer-api.bx/...`),
   который использует сам сайт для отрисовки карточки товара. Быстро, но эндпоинт
   не документирован и может измениться или начать блокироваться антибот-защитой.
2. **`selenium`** — рендеринг страницы в headless Chrome + разбор HTML через
   BeautifulSoup. Медленнее, зато устойчивее к антибот-проверкам.

Режим задаётся `PARSER_MODE` в `.env`:
- `auto` (по умолчанию) — сначала пробует API, при ошибке — Selenium;
- `api` — только API;
- `selenium` — только Selenium.

Так как разметка/эндпоинты OZON могут меняться, при сбоях в первую очередь проверяйте
`app/services/ozon_parser.py` — там вынесены все CSS-селекторы и разбор JSON-ответа.

### Если бот запущен через VPN (обязателен для Telegram), а OZON блокирует VPN-IP

OZON часто блокирует IP-диапазоны VPN/датацентр-провайдеров ещё на уровне TLS-рукопожатия
(и отдаёт decoy-страницу "Похоже, нет соединения" при Selenium-рендеринге) — а Telegram Bot
API при этом может быть недоступен без VPN. В этом случае парсинг можно вынести на отдельную
машину/сеть без VPN, а бот будет обращаться к ней по HTTP:

- **Машина парсера** (без VPN, там, где OZON доступен напрямую): поднимает
  `app/parser_api.py` (`app.parser_main`) — тонкий FastAPI-сервис поверх
  `app/services/ozon_parser.py`, без бота и без БД.

  ```bash
  copy .env.parser.example .env.parser
  # отредактируйте .env.parser — минимум PARSER_API_KEY (общий секрет с ботом)
  docker compose -f docker-compose.parser.yml up --build
  ```

  Сервис слушает `http://<IP-этой-машины>:8001` (`POST /parse`, `GET /health`).

- **Машина бота** (с VPN): в `.env` укажите `PARSER_SERVICE_URL=http://<IP-машины-парсера>:8001`
  и тот же `PARSER_API_KEY`. Бот будет ходить за ценой на удалённый сервис вместо
  локального парсинга — Selenium/`selenium`-контейнер на машине бота уже не нужен.

Если `PARSER_SERVICE_URL` не задан, бот парсит локально как раньше (`PARSER_MODE`/
`SELENIUM_REMOTE_URL`) — обратная совместимость сохранена, разделение полностью опционально.

## Запуск через Docker (рекомендуется)

1. Скопируйте `.env.example` в `.env` и укажите `BOT_TOKEN` (получить у [@BotFather](https://t.me/BotFather)).
2. Запустите:

```bash
docker compose up --build
```

Поднимутся: сам бот, PostgreSQL и Redis. Контейнер `selenium/standalone-chrome`
нужен только для локального парсинга (когда `PARSER_SERVICE_URL` не задан) и по
умолчанию не стартует — поднимайте его явно через `docker compose --profile
local-parser up`, либо разверните парсер отдельно (см. раздел выше про VPN).

FastAPI health-check будет доступен на `http://localhost:8000/health`,
метрики — на `http://localhost:8000/metrics`.

## Локальный запуск без Docker

```bash
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
```

Понадобятся локально запущенные PostgreSQL и Redis (см. `.env.example` для
дефолтных URL) и установленный Chrome (для Selenium-парсера, если он потребуется —
`webdriver-manager` сам подтянет подходящий chromedriver).

```bash
copy .env.example .env
# отредактируйте .env — минимум BOT_TOKEN, DATABASE_URL, REDIS_URL
python -m app.main
```

## Команды бота

| Команда | Назначение |
|---|---|
| `/add` | Добавить товар (ссылка/ID OZON → условие уведомления: мин. цена / процент / оба / по умолчанию 20%) |
| `/products` | Список отслеживаемых товаров |
| `/remove` | Удалить товар из отслеживания |
| `/pause` | Приостановить/возобновить мониторинг |
| `/status` | Состояние системы |

## Как работает мониторинг

`app/scheduler/monitor_loop.py` крутится фоновой asyncio-задачей: раз в
`SCHEDULER_TICK_SECONDS` секунд выбирает из БД товары, у которых истёк их
персональный интервал проверки (`check_interval_seconds`, по умолчанию
`DEFAULT_CHECK_INTERVAL_SECONDS`), и проверяет их параллельно с ограничением
`MAX_CONCURRENT_CHECKS` одновременных запросов (чтобы не словить бан от OZON).

При обнаружении срабатывания порога (цена ≤ мин. значения или падение ≥ заданного
процента) бот делает повторный запрос цены через `CONFIRM_DELAY_SECONDS` секунд —
и только если снижение подтвердилось, отправляет уведомление в Telegram (это
защищает от ложных срабатываний из-за временных сбоев парсинга).

Частота "до 1 раза в секунду" для приоритетных товаров поддерживается через
`check_interval_seconds` / `priority` на конкретном товаре — по умолчанию все
товары проверяются раз в `DEFAULT_CHECK_INTERVAL_SECONDS` (5 минут), чтобы не
попасть под rate limit OZON; выставляйте меньший интервал только для
действительно приоритетных позиций и небольшого числа товаров одновременно.

## Ограничения / что дорабатывать под нагрузку в тысячи товаров

- Текущий планировщик — один процесс с asyncio-семафором. Для нескольких тысяч
  товаров и реальных SLA имеет смысл вынести очередь проверок в Redis
  (например, `rq`/`arq`/Celery) и горизонтально масштабировать воркеры.
- Неофициальный API OZON и Selenium-скрапинг могут блокироваться антибот-защитой
  при высокой частоте запросов — потребуется ротация User-Agent/прокси.
- Миграции схемы БД сейчас делаются через `Base.metadata.create_all` при старте;
  для продакшена стоит добавить Alembic.
